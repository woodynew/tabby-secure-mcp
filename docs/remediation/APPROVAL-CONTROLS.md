# 审批提醒与客户端授权管理

日期：2026-11-15。基于现有内置 HTTP MCP 工作区继续修改；不提交、不发布、不自动安装到个人 Tabby。

## 行为

- 通过 Tabby 公开的 `HostWindowService.bringToFront()`，在显示审批前请求将 Tabby 窗口置于前台。请求过期或已取消时不打扰用户；窗口唤起失败不改变审批结果。没有增加通知权限、Dock 操作或新的运行时依赖。
- 客户端审批、首次 SSH 打开审批和 HTTP 打开请求的等待上限统一为 60 秒，使用同一常量；较短的调用方期限继续生效。命令执行收集仍为 45 秒，其他查询请求仍为 30 秒。
- 在主窗口设置的每个命名客户端下增加授权期限与 Apply 操作：本次会话、从现在起 24 小时、永久、清除授权。修改保持 token 和名称，断开旧会话并取消请求；新代次仅在持久化成功后启用。
- 设置中的“本次会话”批准下一次连接一次，最长 24 小时；再次重连需要审批。未消费的批准只保存在当前运行内存，不写入凭证文件，Tabby 重启后丢弃。
- 清除授权保留凭证但要求下次连接审批；Revoke client 删除凭证；Reset credential 更换 token。其他客户端及 SSH 配置授权不随之改变。

## 安全与回归

权限修改使用既有串行持久化及撤销版本屏障。同步失效旧会话，写入失败保持运行中拒绝，旧事务不能恢复后来发生的撤销。磁盘仍使用既有 v1 凭证文件结构；一次会话批准不引入磁盘迁移。

已先取得前台提醒/一分钟校验和授权期限操作的失败回归，再实现并复测。回归覆盖：60 秒边界和较短调用期限、已取消/过期时不唤起、唤起失败、token 不变、期限切换、会话批准仅消费一次且不跨重启、保存失败、写入后同步失败、撤销交错，以及真实 HTTP 旧会话/请求失效和其他客户端保持可用。

独立审阅发现并修复两项 P2。第一项：期限保存失败后，另一客户端的成功保存不应删除原凭证。新增重命名、新建、授权保存三种交错回归；无关保存保留 token，并把该凭证的磁盘授权安全降为 none，当前运行继续拒绝，直到明确重试成功。第二项：较旧的期限修改推进 generation 后，较新的修改仍需完成落盘。入口保持严格版本校验，队列执行绑定同一 token 和最新 revision，使用当前代次继续提交；新 none/24h/session 均覆盖旧 permanent，重启不恢复旧授权。真正的 revoke/reset 仍保留原失效语义。独立复核已关闭两项发现，本轮有限范围未遗留确认的 P1/P2。
